# Minimal Agent V0 Design

[中文](design.md) · English

Purpose: a one-shot Rust executable `ma`, callable by people and programs through arguments, stdin, stdout and stderr. One model. One tool. One loop, permanently.

## Established boundaries

- The only model protocol is OpenAI-compatible Chat Completions; synchronous SSE streaming is the default, with no SDK, and endpoints returning plain JSON are still supported.
- The only tool is `shell(command)`. The loop only requests the model, runs the tool, appends the tool result and prints the final answer.
- macOS and Linux are the V0 targets. Windows is not implemented for now. No Session, Memory, MCP, Planner, Provider abstraction, GUI or resident background work. Skills support loading instructions only after an explicit command-line selection.
- Synchronous HTTP; a small number of plain functions, with the loop and permission logic in `src/main.rs` and skill loading plus prompt assembly in `src/skills.rs`.
- By default the workspace is read-only, writes are denied and shell network access is denied. Model HTTP requests are unaffected by the shell network switch.
- The user has been explicit: `--write` grants write permission only for the current working directory at startup and its descendants. `--skills` adds read-only access for the selected real skill directories and adds no custom write directory.
- The config file supplies connection settings only (`base_url`, `api_key`, `model`), defaults to `~/.config/ma/config.json`, and can be overridden with `MA_CONFIG`; permissions can never come from the config file.
- Permissions are fixed at startup and are never asked for or upgraded while running. The same Policy produces the model instruction and drives the Guard.
- The Guard blocks obvious violations, including path checks on common write commands and redirections; it uses canonical paths to check existing paths and symlinks. Unknown executables, side effects inside a program and dynamic shell computation cannot be judged reliably by static inspection, so it is not an OS sandbox.
- Read-only file commands may use working-directory globs; before execution they are matched component by component and directory and symlink boundaries are checked, with a scan budget of 16384 directory entries per argument. Quoting keeps its meaning; a character range mixed with quoting is conservatively refused. Write targets still accept literal paths only. The Guard matches characters according to the host locale: consistent with `bash` and busybox `ash`, whereas Debian/Ubuntu `dash` handles `?` bytewise, so UTF-8 file names do not match there and the Guard likewise does not expand those candidates.

## Runtime contract

- `--base-url`/`BASE_URL`, `--api-key`/`API_KEY`, `--model`/`MODEL`; model settings read only these three environment variables, with no prefixed or legacy fallbacks. The config file supplies the same three keys at lower precedence.
- `--skills name1,name2` looks up `.agents/skills/` in the startup cwd and then `$HOME/.agents/skills/` by directory name only; the project wins, an unreadable entry falls back, and a second failure is skipped. Without the option nothing is loaded. The full `SKILL.md` and its real directory enter the skills section of the system prompt, keeping the two initial messages (system, user) and the existing recovery contract; skills count as irreducible, appear only in the exit diagnostic, and are never truncated automatically. Resources are read on demand through the shell with no pre-run scripts, no permission frontmatter parsing and no new tools registered. 64 KiB per file and 1 MiB of raw instructions in total; loads and skips are recorded only in verbose mode. Custom directory input is not supported yet.
- The base URL is the API root, for example `https://example.com/v1`, and the client appends `/chat/completions`.
- The prompt comes from positional arguments; non-terminal stdin is supplementary text, and stdin alone is also accepted. Input is limited to 1 MiB; shell stdin is always closed so an interactive command cannot wait forever.
- help / version may appear after the prompt and are handled before configuration and input are read; values of other options are skipped, and `--` separates the prompt.
- stdout carries the complete final answer only; stderr carries local errors. `--verbose` / `-v` appends model text, rounds, shell commands, tool output and results live. Process logging is off by default and no logging framework is introduced. Exit 0 on success, 2 for argument/input errors, 1 for HTTP/protocol errors, 3 when steps are exhausted.
- `max_steps` defaults to 200 and counts model requests. The last step does not execute a tool call whose result could not be fed back to the model.
- Requests use `stream: true`; SSE is parsed by event rather than transport chunk, accepting UTF-8, a leading BOM, LF/CRLF/CR, heartbeats and usage-only chunks. content, reasoning_content, refusal and tool arguments keyed by index are accumulated separately; extra fields are preserved and merged recursively for objects, and conflicting values exit as a protocol error. Both `finish_reason` and `[DONE]` must appear for a response to count as complete. Tools are run only after the response is fully received and validated; a broken stream prints no partial final and runs no partial tools. A whole response is still limited to 4 MiB, and the HTTP timeout covers streaming reads. Verbose output is best-effort and does not wait when the pipe is full, so request reads and shell timeouts are unaffected.
- HTTP timeout defaults to 120 seconds and shell timeout to 30 seconds, adjustable with startup options and required to be greater than zero.
- Shell stdout and stderr each keep at most 64 KiB; beyond that the pipe is still drained and truncation is marked, with no long-lived background reader thread.
- The Unix shell uses `/bin/sh -c` with cwd fixed to the startup directory; a separate process group allows descendants to be cleaned up after a timeout. The model API key environment variable is not passed to the shell.
- The shell's `CDPATH` is cleared and `cd` supports simple sequential execution only; a `cd` mixed with a pipeline, a background branch or `||` is refused. `ln` and download forms whose write target cannot be determined are refused, to avoid an obvious gap in path checking. A full shell and the internal state of an executable are still not simulated.
- On SIGINT / SIGTERM / SIGHUP the current tool process group is cleaned up and the process exits with `128 + signal`; SIGKILL and processes that leave the group carry no strong guarantee.
- A tool result is a JSON string with stdout, stderr, exit_code, timed_out and truncated; refusals and execution errors are fed back to the model as tool results too.
- Multiple tool calls run in the order they were returned and are fed back one by one. Assistant messages (including compatibility fields such as reasoning_content) are preserved; tool IDs, tool names, arguments and the final finish_reason are validated so that a wrong ending or an unknown tool cannot be executed.
- Ordinary HTTP errors are not retried; only an explicit context-too-long error triggers recovery. Recovery is a three-tier ladder ordered by information cost, and each tier keeps system, the original user message and the newest tool turn as late as it can: (1) compact every tool call outside the newest turn into a one-line skeleton (command, exit code, stdout/stderr byte counts, timeout and truncation markers) written into a replaceable summary slot at index 2, rebuilt rather than appended, capped at 64 KiB, losing output bodies only, deleting no turn and re-running no command; (2) truncate the head and tail of the newest turn's tool results by 2 KiB each, preserving exit code, status markers and the tool_call_id pairing, leaving the assistant message carrying tool_calls untouched; (3) truncate the head and tail of the original input by 32 KiB each. Tier 3 is data destruction (piped input never landed on disk and the omitted part cannot be re-read) and warns on stderr unconditionally, not gated on verbose. Each tier leaves a recognisable marker, which is how the ladder guarantees idempotence, never trims the same bytes twice and never piles up summary slots. Each context failure applies one tier and retries the model once, with a new error continuing from the tier that just ran; when all three are exhausted and the history still cannot change, the byte counts of every irreducible part are reported before exiting. Shell commands are not replayed and the retry counts towards max_steps. There is no proactive trimming, model summarisation, tokenizer or new configuration.
- Recovery does not rewrite the system prompt, so loaded skill instructions are never removed by context recovery; the total skills size (1 MiB), like the original input, counts as irreducible, its byte count is reported only in the exit diagnostic, and it is never truncated automatically.
- `--update` takes the artifact for this platform from the latest GitHub release and replaces itself in place. The only criterion is the artifact itself: the candidate is first written to a temporary file in the target directory and run with `--version`, and it may replace the binary only when it reports the string equal to the version the API announced; a failure cleans up and keeps the original. A truncated download, an artifact for the wrong architecture and an HTML error page therefore cannot displace a working `ma`. The archive accepts only a plain `ma` at the root or under a single directory, and any member containing `..`, an absolute path or a deeper path is refused. Production requests force https and follow redirects (a GitHub asset download 302s to a CDN); the local http address injected by tests is the only exception. When invoked through a symlink the target is replaced and the link stays. An ordinary run checks once a day for a new version, the notice goes to stderr only, the timestamp is `~/.config/ma/last-update-check`, and any failure is silent; `--no-update-check` turns it off.

## Acceptance

End-to-end local mock HTTP tests verify the wire protocol, stdin, multiple rounds and tools, permission refusals, the step limit, errors and timeouts, as well as SSE transport fragmentation, interleaved tool arguments, a broken stream, the total byte budget and verbose text being visible before upstream finishes; the context recovery part verifies the ladder's escalation order and idempotence (repeated recovery never trims the same bytes twice and never piles up summary slots), that the tool call and result ID pairing survives truncation, the unconditional stderr warning when the original input is truncated, the irreducible byte buckets in the exit diagnostic, and that ordinary HTTP errors never touch the history; real shell tests verify live output, timeouts, truncation and directory boundaries. Run fmt, clippy, cargo test and a release build, then measure the size: target <5 MB, hard limit <10 MB. macOS is accepted on this machine, Linux through CI or a one-off container, and a cross-platform or private-endpoint test that was not actually run must not be claimed as passing.
